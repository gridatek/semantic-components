# Finding shadcn Styles

How to find shadcn/ui's styles and compare them with ours. Rewritten 2026-11-04: the reference is now a generated app, one per style, and our looks live in our styles (`@semantic-components/styles`).

## The reference: a generated app per style

Not shadcn's GitHub source, not its website: **`D:/Workspace/Projects/shadcn-reference`** ([klagrida/shadcn-reference](https://github.com/klagrida/shadcn-reference)), made with shadcn's own CLI.

| Folder                   | What                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------- |
| `presets/<style>/`       | One app per style — nova, vega, maia, lyra, mira, luma, sera, rhea — on **Base UI** |
| `presets-radix/<style>/` | The same on **Radix**, for the components whose Radix look we follow (the Select)   |

In each app, `src/components/ui/*.tsx` holds every component with its **classes written out in full**: the CLI has resolved shadcn's `cn-*` names (in its source, the looks live in `registry/styles/style-*.css`) into plain Tailwind classes. So:

- **Read the `.tsx`**, class for class — no theme CSS to look up.
- **One style against another** is a diff of two files (`diff presets/nova/… presets/maia/…`).
- **The classes are already RTL-ready**: the CLI ran with `--rtl`, so they are logical (`ms-*`, `pe-*`, `start-*`, `text-start`) with `rtl:` variants where needed (`rtl:translate-x-1/2`, `rtl:rotate-180`) — compare them with ours as they are.
- The theme (its CSS variables: colours, radius, fonts, charts, sidebar): `src/styles.css`.

Regenerate with its `setup.sh` (`sh setup.sh`, `sh setup.sh vega maia`, `BASE=radix sh setup.sh`), or refresh one app inside it with `npx shadcn@latest add --all -y -o` and read the `git diff`.

shadcn's docs and **examples** are still on GitHub — `apps/v4/content/docs/components/base/<name>.mdx` (the page: which examples, in what order) and `apps/v4/examples/base/<name>-*.tsx` (each example):

```bash
gh api repos/shadcn-ui/ui/contents/apps/v4/examples/base/card-image.tsx --jq '.content' | base64 -d
gh api repos/shadcn-ui/ui/contents/apps/v4/examples/base --jq '.[].name' | grep '^card'
```

For a component's parts and behaviour, Base UI's own docs are in the reference app's `node_modules`: `presets/nova/node_modules/@base-ui/react/docs/react/components/<name>.md`.

## Where our looks live: styles

shadcn's eight styles are our **styles** (`@semantic-components/styles`), one chosen when the app starts (`provideSemanticComponents({ preset: { style } })`, nova by default).

- **`libs/styles/<style>/src/<component>.ts`** — the classes of a component that change from style to style, one file per component per style, each generated from that style's `.tsx` in the reference app (the source in its header comment). A `cva` where shadcn has one (`button`, `badge`, `alert`), strings otherwise.
- **`libs/styles/src/index.ts`** — the `ScStyle` interface: every key (`button`, `card`, `table`, `alertDialog`, `backdrop`, `avatarGroupCount`…).
- **The part reads its style**: `injectStyle().card`, then `cn(this.styles.title, this.classInput())`. Classes that are the same in every style stay in the part.

So when a component's turn comes:

1. Diff its `.tsx` across the eight styles: what differs goes into the style, what's the same stays in the part.
2. Write the style files from the `.tsx` with a small script (one per component, kept out of the repo) — never by hand — so each class is shadcn's exactly.
3. Leave out what our machinery does instead (below), and say so in the style file's comment.
4. A styles spec checks the style's classes on the rendered part (`apps/showcase-e2e/src/styles/<name>.spec.ts`, run once per `styles-…` project; read the style with `currentStyle()`).

## RTL: what must stay physical

The reference's classes are logical already; so are ours. A physical class in our code (`pr-*`, `left-*`, `text-right`) is a bug — the repo is RTL-first — with four exceptions, kept physical on purpose:

**1. Centring: `left-1/2` paired with `-translate-x-1/2`.** `translate-x` has no logical form, so changing only the inset moves the element off-centre in RTL. shadcn's output keeps the inset logical and adds `rtl:translate-x-1/2`; if you convert the inset, do both. Affects tooltip, radio, the resizable handle and toast-stack's centre positions.

**2. Explicitly physical APIs.** Where a component takes a side by name — `side="left"`, `swipeDirection="left"`, `'top-right'` — the caller means literally left. Affects drawer, sheet, sidebar and toast-stack.

**3. Spatial widgets.** Image cropper, image compare and org-chart: handle offsets pair with physical resize cursors (`w-resize`), and mirroring a crop box or a diagram is wrong whatever the writing direction.

**4. Anything an overlay is coupled to.** The media progress fills are positioned over a slider; flipping one without the other's thumb math would desync them.

The test: is the edge _the trailing one_ (flip it) or _a specific physical side_ (leave it)?

For background, shadcn's mapping table is `packages/shadcn/src/utils/transformers/transform-rtl.ts` (`pl-` → `ps-`, `space-x-*` → `rtl:space-x-reverse`, `cn-rtl-flip` → `rtl:rotate-180`…).

## CSS variables

shadcn's keep their names; everything else takes an **`--sc-` prefix**, so a variable says whose it is (the user, 2026-11-17).

- **shadcn's, unchanged**: the theme's tokens (`--background`, `--primary`, `--radius`, `--chart-1`…, `--sidebar-*`) and the variables its components set (`--sidebar-width`, `--sidebar-width-icon`, `--skeleton-width`, `--cell-size`, `--cell-radius`, `--card-spacing`, the Toggle Group's `--gap`, `--ratio`, `--drawer-inset`, Typeset's `--typeset-size`, `-leading`, `-flow`, `-font-body`, `-font-heading`, `-font-mono`, `-muted`, `-rule`).
- **Base UI's, prefixed**: Base UI sets them at runtime; here our parts do, so they are ours — `--sc-transform-origin`, `--sc-scroll-area-overflow-{x,y}-{start,end}`. A snippet or style string from shadcn that reads one is renamed (`origin-(--transform-origin)` → `origin-(--sc-transform-origin)`); its README says which name it replaces.
- **Ours, prefixed, with the component's name**: `--sc-success`, `--sc-warning`, `--sc-editor-highlight-1`, `--sc-confetti-1`, `--sc-chart-bar-radius`, `--sc-typeset-radius`, `--sc-slider-thumb`, `--sc-color-picker-track`… Tailwind's own namespaces stay Tailwind's (`--color-success: var(--sc-success)` keeps `bg-success`).
- Not ours to rename: other libraries' contracts (Shiki's `--shiki-*`, pdf.js's `--total-scale-factor`, `--scale-round-*`) and an app's own variables (`--page-gutter`).

## Deliberate divergences

Do **not** "fix" these to match shadcn:

- **The theme is each app's** (`apps/*/src/styles.css`), not the library's: shadcn's colors exactly, from the reference app, plus our `--sc-success` / `--sc-warning` (the toast's) and the editor's colours (highlights `--sc-editor-highlight-1` to `-5`, search matches `--sc-editor-search-match` and `--sc-editor-search-current`, light and dark). `--muted-foreground` is darker (`oklch(0.51 0 0)`) and `--destructive` too (`oklch(0.52 0.245 27.325)`), for 4.5:1 contrast.
- **Contrast over opacity** — where shadcn dims text with opacity (`opacity-60`, `text-muted-foreground/70`), we keep `text-muted-foreground` so the text keeps 4.5:1, and dim only what isn't text (Trace: a pending line's icon).
- **Placement and open/close animation are Angular's and the CDK's** — shadcn's `fixed top-1/2 start-1/2 -translate-*` (placement) and `data-open:` / `data-closed:` classes (animation) are left out of the styles: the CDK overlay places (centres a dialog; a select's list from its `positionChange`), Angular's `animate.enter` / `animate.leave` animate. Alert Dialog, Select. **A dialog's width** (2026-11-11): shadcn's `w-full` fills a fixed, screen-wide box; the CDK's pane is only as wide as its content, so `scDialog` and `scAlertDialog` add `w-screen` (after the style, before your classes) and the style's `max-w` caps it — a dialog with short content is as wide as shadcn's, and doesn't collapse while zooming in.
- **A modal's scroll lock is the CDK's: the page's scrollbar stays** (the user, 2026-11-06: follow the CDK; the difference is only styling) — Base UI hides it while a modal is open (`useScrollLock`: `overflow: hidden` on the page's scroller, `scrollbar-gutter: stable` on `html` so nothing shifts). Our modals (Dialog, Alert Dialog, Sheet, Drawer) use the CDK's `block()` strategy: `html.cdk-global-scrollblock` is `position: fixed; width: 100%; overflow-y: scroll`, so the scrollbar stays, inactive, beside the panel. An app that wants it hidden can override that class in its styles (`overflow-y: hidden; scrollbar-gutter: stable`).
- **One backdrop for every overlay** — shadcn's overlay is the same in Alert Dialog, Dialog, Sheet and Drawer for a style, so it is one style key (`backdrop`), read by the shared `scBackdrop` itself.
- **Button: `aria-disabled` styled too** — `scButton` sets `aria-disabled` with `disabled`, so its style adds `aria-disabled:pointer-events-none aria-disabled:opacity-50` beside shadcn's `disabled:` ones (`libs/styles/*/src/button.ts`).
- **Link: a link by default, button looks as variants** (the user, 2026-11-11) — shadcn has no link component: a link that looks like a button is an `<a>` given `buttonVariants()`, and `link` is one of the Button's variants. Our `a[scLink]` is a link by default (`variant="default"`, the button style's `link` look), and a button's look is a variant: `button` (the primary one, shadcn's `default`), `outline`, `secondary`, `ghost`, `destructive` (`LINK_TO_BUTTON` in `link.ts`). `scButton` keeps shadcn's variants, `link` included.
- **Input Group: no InputGroupInput or InputGroupTextarea** — ours are plain `scInput` / `scTextarea` (and any control with `data-slot="control"`); the group gives them those classes (`[&>input[data-slot=control]]:…`), from each style's InputGroupInput / InputGroupTextarea. shadcn's `data-slot="input-group-control"` is our `control`. The group also rings for a focused date/time segment or a select, multiselect or combobox trigger.
- **Control Group (shadcn's Button Group): its name, children by position** — named for what it is for, an input or a select joined with its buttons. Its children are found by position (`[&>*:not(:last-child)]`), not by `data-slot`; where luma, rhea and sera read `[data-variant=outline]` on a child, ours read `[data-slot=button]` (our buttons carry no `data-variant`).
- **Select: Radix's styles, not Base UI's** (the user's choice, 2026-10-30), from `presets-radix/<style>/select.tsx`, **built the Angular way**: the highlighted item reads `data-[active=true]:` for `focus:` and `aria-disabled:` for `data-disabled:`; nothing of Radix's machinery is recreated (its `--radix-select-*` variables dropped — the CDK sets the transform origin, the height and the width). The root sets the width, the trigger fills it, the list matches it.
- **Table: the container is a part, and can be framed** — shadcn's Table wraps itself in its scrolling div; a directive on `table` can't, so `scTableContainer` is the consumer's. A frame round it is `scFrame` (below).
- **`scFrame`: one frame for framed boxes** (the user, 2026-11-04) — shadcn's examples hard-code a frame (`rounded-md border`, `rounded-lg`) that suits few styles; ours is a directive, `scFrame`, drawing the style's `frame` — the style's card radius, ring and shadow — round any box: an aspect ratio, a table's container. Only the look: clipping is the box's (the aspect ratio clips, the table's container scrolls). Other hand-drawn frames move to it case by case, in each component's turn. The Card draws its own frame from the same key (its `card` style holds the rest), so the card's frame is in one place.
- **Alert: no `role="alert"`** — shadcn's always has it; ours has none, and the consumer announces one that appears (`role="status"` or `role="alert"` on a wrapper — the Alert page's Announcing section).
- **Avatar: Base UI's image loading** — the image rendered at once over its fallback, hidden by `visibility` while `data-loading` / `data-error` (shadcn's preloads, then swaps). The group count is the only style key: shadcn's avatar is the same in every style but for it.
- **Notification Center's count: its own pill** — it doesn't take the badge's style (sera's badges are bare text): a counter keeps a filled pill in every style.
- **Menu (shadcn's Dropdown Menu): `data-highlighted:` for `focus:`** — an item is highlighted when Aria makes it active, not when it has focus (after a click open none is), so the styles read `data-highlighted:` for `focus:`, `aria-disabled:` for `data-disabled:`, `aria-expanded:` for `data-popup-open:` (a submenu's item), `group/menu-item` for `group/dropdown-menu-item`. Placement and animation classes are left out (above). A submenu sits 4px from its menu's edge in every style and direction, its first row level with the item that opens it (the user, 2026-11-05) — shadcn places it against its item (`sideOffset={0}`, `alignOffset={-3}`), so its gap and its height follow each style's padding.
- **Menubar: the Menu's parts, a focus ring** — no MenubarItem, MenubarCheckboxItem…: the Menu's parts take the style's `menubar.menu` look inside a bar (shadcn's menubar classes merged over its dropdown ones, as its parts wrap them). Its triggers add `focus-visible:outline-2 focus-visible:outline-ring`: shadcn's have none (`outline-hidden`).
- **Context Menu: the Menu's parts, a focusable area** — no ContextMenuItem…: the Menu's parts take the style's `contextMenu` look in a context menu. Its area (`scContextMenuTrigger`) is focusable — Shift+F10 and the Menu key open the menu — so it adds `focus-visible:ring-3 focus-visible:ring-ring/50`; shadcn's has `select-none` only. `side` is logical (`start` / `end`).
- **Tabs: our states** — `aria-selected:` for `data-active:`, and the root's `data-[orientation=…]` for `data-horizontal:` / `data-vertical:` (`libs/styles/*/src/tabs.ts`). A hidden panel is `inert`, so the part adds `[[inert]]:hidden`.

- **Dialog: the ✕ is in your markup, placed by the dialog** — shadcn's `DialogContent` draws its ✕; ours is your button with `scDialogClose` (the style's button, ghost / icon-sm), put in the corner by the dialog (the style's `close`, as `[&>[data-slot=dialog-close]]:` classes).

Two additions, the rest of the file shadcn's: `[data-typeset]` beside shadcn's selector in the elements' block (`:is(.typeset *:not(…), [data-typeset])`), and the container's defaults on `:where(:root)` (outside a container nothing sets the variables; zero specificity, so yours win). Any element can take it (`<p data-typeset>`) with no new selector; what it can't have is what depends on its neighbours or children in a container (a list's items, a heading's code). **Its variables are the style's** (the user, 2026-11-16): shadcn sets them on `.typeset` in its file; ours are in each style's `typeset-variables.css` (`libs/styles/<style>/src/typeset-variables.css`, on `:where(:root)`), with the corners of the style's own Code Block and Kbd (`--sc-typeset-radius`, `--sc-typeset-radius-inline`; square in lyra and sera) — highlights (`mark`) take the inline ones too, where shadcn has a fixed 0.2em. Headings h1 to h4 take the style's weight, tracking and case (`--sc-typeset-heading-weight`, `-tracking`, `-case`; 600, normal, none, and in sera uppercase and 0.05em, as its titles: `tracking-wider uppercase`) — shadcn's Typeset has none of these — ui's file holds the rules only, and an app imports both. The showcase links its style's file at start (`provideTypesetStyles`, the `typeset-variables-<name>` bundles).
- **Scroll Area: Base UI's parts, a default scrollbar, plain classes** (the user, 2026-11-17; checked against shadcn's registry in the eight styles the same day: the root, viewport, scrollbar and thumb classes match, the thumb `rounded-none` in lyra and sera) — shadcn's ScrollArea renders the viewport, a vertical scrollbar and the corner; ours renders the scrollbar (and its thumb) by default, which any scrollbar or corner you write replaces, and the viewport is yours (it wraps your content). What Base UI sets inline is classes here: the viewport's `overflow-auto` and hidden native bar, the scrollbar's `absolute` and its edges (`end-0 top-0 bottom-(--sc-scroll-area-corner-size)`), chosen by orientation in the part (plain classes, not `data-vertical:`), `border-s` for shadcn's `border-l` (the reference app's RTL form). The root is `relative` only, as shadcn's: an `overflow-hidden` there clipped the viewport's focus ring.
- **The browser's scrollbars in the style's look** (the user, 2026-11-17) — shadcn styles no native scrollbar: its parts carry `scrollbar-thin` or `no-scrollbar`, and its Scroll Area draws one. Ours: ui's `scrollbar.css` puts the Scroll Area's thumb on every native bar (`::-webkit-scrollbar`: 10px, no track, inset 1px, the theme's border colour; the corners from the style's `scrollbar-variables.css`), Firefox's thin bar in the same colours. So the parts set no `scrollbar-width` of their own (it would make Chromium drop `::-webkit-scrollbar`): `scrollbar-thin` is left out of the `codeBlock` styles' strings.
- **Decomposition** — shadcn ships one function per part in one file; we split into directives, one per file, so one shadcn part can map to several of ours.
